# Технічний звіт — ridetoalps.com

Знято 26 листопада 2026 року.

Усі перевірки виконані проти **опублікованого домену** `https://ridetoalps.com`,
а не проти тестового середовища. Там, де число знято з локальної збірки, це
написано окремо і вказано, чому.

Кожен розділ — це тека з первинними даними: заголовки відповідей, збережений
HTML, звіти Lighthouse, скріншоти. Нічого з цього не переписано вручну, усе
згенеровано скриптами, які лежать у корені проєкту і які можна перезапустити.

---

## Головне, що треба знати перед читанням

**На хостингу стоїть не та збірка, яку перевіряли й доробляли.** Це не здогад,
це видно ззовні, і з цього випливають три конкретні наслідки:

| Що саме | Наслідок | Доказ |
|---|---|---|
| Теку `/blog/` не залито | Три англомовні статті блогу віддають **404**, хоча сторінка `/blog.html` на них посилається | `d1-crawling/live-sweep.txt` |
| `.htaccess` без правила `www` | `https://www.ridetoalps.com/` віддає **200** — той самий сайт на двох адресах, це дублікат для пошуковика | нижче, D1 |
| Нову версію сторінок не залито | Подій GA4 (`quote_shown`, `calc_started`, `whatsapp_click`, `booking_request_submit`) на сайті **немає**; розмітки `TaxiService` / `Organization` теж немає | D4, D8 |

Усе це вже зроблено у проєкті й перевірено. Лишилося залити. Команда, яка
збирає теку для вивантаження:

```
node build-deploy.mjs
```

Після заливки варто перезапустити перевірки — вони перезапишуть цей звіт
свіжими числами з живого домену:

```
node d1-live-sweep.mjs     # усі адреси sitemap на живому домені
node d3-indexnow.mjs       # ключ IndexNow і тестове надсилання
node d5-median.mjs         # PageSpeed, по три проходи на сторінку
node d8-validate.mjs       # структурована розмітка
```

## D1 — Доступ для пошукових і AI-ботів

**Тека:** `d1-crawling/`

| Вимога | Стан |
|---|---|
| `robots.txt` доступний і не блокує обхід | виконано |
| `sitemap.xml` доступний і вказаний у `robots.txt` | виконано, 67 адрес |
| Доступ для Googlebot, Bingbot і AI-ботів | виконано |
| Усі сторінки віддають 200 | **64 з 67** |
| Коректні 301 замість ланцюжків редиректів | виконано |
| Одна канонічна адреса домену | **не виконано на хостингу** |

`bot-access.txt` — це відповіді сервера на запити з User-Agent Googlebot,
Bingbot, GPTBot, ClaudeBot, PerplexityBot і Google-Extended. Жоден не
отримує 403 чи 404: перевірявся саме доступ, а не текст `robots.txt`.

`live-sweep.txt` — усі 67 адрес із sitemap, по черзі. Не віддають 200 три:

```
404  https://ridetoalps.com/blog/munich-airport-to-alps-transport-options.html
404  https://ridetoalps.com/blog/munich-airport-ski-luggage-arrivals.html
404  https://ridetoalps.com/blog/alpine-winter-driving-vignettes-chains.html
```

Німецькі, російські й українські статті на місці — не залито тільки
англійську теку `/blog/`. Це підтверджується й з іншого боку: у
теці `update 2/`, якою робили останнє вивантаження, є `de/blog`, `ru/blog` і
`uk/blog`, а англійської `blog/` немає взагалі. Сторінка `/blog.html` посилається на ці три адреси,
тобто зараз на сайті три непрацюючі посилання, і вони ж лежать у sitemap, який
ми віддаємо пошуковику.

**Канонічна адреса.** Зараз:

```
http://ridetoalps.com/        301 → https://ridetoalps.com/     коректно
http://www.ridetoalps.com/    301 → https://www.ridetoalps.com/ лишається на www
https://www.ridetoalps.com/   200                               дублікат
```

Сайт відкривається і на `www`, і без нього, обидві адреси віддають 200. Для
пошукової системи це дві копії одного сайту. Правило, яке зводить усе до
адреси без `www`, додане в `.htaccess` у проєкті й чекає на заливку.

## D2 — Вміст у вихідному HTML

**Тека:** `d2-html/`

| Вимога | Стан |
|---|---|
| Тексти, ціни й FAQ присутні у сирому HTML, а не домальовуються скриптом | виконано |
| Сторінка читається без JavaScript | виконано |

У теці лежить HTML чотирьох сторінок рівно таким, яким його отримує робот, —
без виконання жодного скрипта. `content-checks.txt` показує витяги: заголовки,
таблицю цін усіх десяти напрямків, перше питання FAQ разом із відповіддю.

`no-js-screenshots/` — ті самі сторінки у браузері з **вимкненим JavaScript**.
Сторінка лишається читабельною і заброньованою не через скрипт: видно ціни,
тексти, контакти. Калькулятор без JS не рахує — це нормально, — але базова
ціна напрямку все одно є в HTML.

## D3 — IndexNow, Search Console, Bing Webmaster Tools

**Тека:** `d3-indexnow/`

| Вимога | Стан |
|---|---|
| Ключ IndexNow у корені сайту | створено, **чекає на заливку** |
| Скрипт надсилання адрес | виконано — `indexnow.mjs` |
| Скріншоти Search Console і Bing Webmaster Tools | **надати не можемо** |

Ключ згенеровано, файл названо самим ключем, усередині — той самий рядок, як
того вимагає протокол. Сам ключ у звіті не наводиться, як і просили.

Тестове надсилання вже виконано: API IndexNow прийняв усі 67 адрес і повернув
`202 Accepted` — заявку взято, ключ перевіряється. Перевірка показала, що файл
ключа на хостингу поки віддає 404, тобто валідацію він не пройде, доки його не
залито. Після заливки достатньо запустити `node indexnow.mjs`.

IndexNow спільний для Bing, Yandex, Seznam і Naver. Google до нього не
підключений — для Google працюють sitemap у `robots.txt` і Search Console.

**Скріншотів із Search Console і Bing Webmaster Tools у звіті немає.** Доступу
до цих кабінетів у нас немає, а намалювати їх — це не доказ. Усе, що залежить
від сайту, зроблено і перевіряється ззовні: sitemap доступний, вказаний у
`robots.txt`, адреси канонічні, розмітка валідна. Лишилося один раз додати
домен у два кабінети й підсунути туди sitemap — покроково описано в
`d3-indexnow/indexnow.txt`.

## D4 — Події GA4

**Тека:** `d4-analytics/`

| Подія | Стан у збірці | Стан на хостингу |
|---|---|---|
| `page_view` | працює | **працює** |
| `calc_started` | працює | відсутня |
| `quote_shown` | працює | відсутня |
| `whatsapp_click` | працює | відсутня |
| `phone_click` | працює | відсутня |
| `deposit_click` | працює | відсутня |
| `booking_request_submit` | у коді | відсутня |

`ga4-events.txt` знято у справжньому браузері: сторінку відкривають, тицяють у
калькулятор, перемикають поїздку туди-назад, натискають контакти — і кожна
подія фіксується **на двох рівнях одночасно**: що сайт передає в `gtag` і що
реально йде запитами на сервери Google. GA4 надсилає події пакетами, тому
самого мережевого зрізу було б замало.

Приклад записаного розрахунку туди-назад:

```
подія: quote_shown
  route = "Munich Airport (MUC) ⇄ Kitzbühel"
  destination = "Kitzbühel"
  value = 540
  currency = "EUR"
  passengers = 3
  vehicles = 1
  return_journey = true
  return_discount = 60
  night_or_group_rate = false
```

Три речі, які варто сказати прямо:

- **`deposit_paid` свідомо не реалізовано.** Посилання веде на сайт PayPal, і
  назад сторінка не отримує жодного сигналу про успішну оплату. Клік — це не
  оплата, тому подія чесно називається `deposit_click`. Для `deposit_paid`
  потрібен return URL від PayPal або webhook на сервері.
- **`booking_request_submit` не відтворюється автоматично** — вона спрацьовує
  тільки після реальної відповіді від `send-form.php`, тобто після справжньої
  заявки в Telegram. Код наведено у звіті.
- **Дублі з GTM.** Контейнер `GTM-TC59WJXP` сам шле `click_whatsapp` і
  `click_phone`, які дублюють наші `whatsapp_click` і `phone_click`. Варто
  лишити одну пару, інакше кліки рахуватимуться двічі.

Скріншотів з інтерфейсу GA4 немає з тієї ж причини, що й у D3 — немає доступу
до облікового запису. Мережевий зріз показує рівно те саме, що показав би
DebugView, тільки незалежно від кабінету.

## D5 — Швидкість і мобільна версія

**Тека:** `d5-performance/`

Інструмент — Lighthouse, той самий рушій, що рахує лабораторну частину
PageSpeed Insights. Профіль Mobile: екран 412×823, CPU уповільнено вчетверо,
мережа Slow 4G. **По три проходи на сторінку, у таблиці медіана.**

Три проходи — не формальність. Два послідовні заміри тієї самої адреси дали
LCP 5,03 с і 1,89 с: час відповіді цього хостингу стрибає, і одне число нічого
не доводить.

### Опублікований домен — зараз

| Сторінка | Performance | LCP | CLS | TBT |
|---|---|---|---|---|
| головна | 85 | **4,21 с** | 0,000 | 145 мс |
| Kitzbühel | 86 | **4,04 с** | 0,000 | 68 мс |
| Salzburg | 81 | **4,93 с** | 0,000 | 88 мс |

Performance усюди вище 80 — критерій виконано. CLS нульовий. А от **LCP не
відповідає ТЗ на жодній із трьох сторінок** (треба ≤ 2,5 с).

### Та сама перевірка на поточній збірці

| Сторінка | Performance | LCP |
|---|---|---|
| головна | 97 | 2,33 с |
| Kitzbühel | 99 | 1,65 с |
| Salzburg | 99 | 1,65 с |

Що саме було не так і що з цим зроблено:

1. **Стилі блокували показ сторінки.** Головна завжди тримала CSS усередині
   сторінки, а всі згенеровані сторінки тягнули `route.css` окремим запитом.
   Хостинг працює по HTTP/1.1, тобто цей запит не йде паралельно з документом:
   браузер чекає на нього, перш ніж щось намалювати. Контрольний замір на
   локальному сервері, по три проходи:

   | | з окремим `route.css` | зі стилями всередині |
   |---|---|---|
   | FCP | 1,84 с | 1,26 с |
   | LCP | 2,48 с | 1,65 с |
   | Performance | 96 | 99 |

   Тепер стилі вбудовані в усі 56 згенерованих сторінок. `route.css` лишився
   єдиним джерелом правди — збірка читає його і вставляє, редагувати так само
   треба одне місце.

2. **AVIF не кешувався взагалі.** У `.htaccess` не було ні типу, ні правила
   кешування для `.avif`, тож головне фото сторінки — те саме, що є LCP-
   елементом, — довантажувалося заново при кожному заході. Додано тип і
   кешування на рік.

3. **Великі фото віддавалися телефону в повну ширину.** Фото міста і фон
   CTA-блока віддавалися на 1200–1376 px там, де телефон показує їх на ~370 px.
   Для фото міста потрібні розміри вже лежали на диску й просто не
   використовувалися; для CTA їх згенеровано.

   | | було | стало на телефоні |
   |---|---|---|
   | герой маршруту | 85 KB | 34 KB |
   | фото міста | 137 KB | 36 KB |
   | фон CTA | 89 KB | 38 KB |

Локальні числа не мають мережевої затримки до хостингу, тому це не обіцянка
конкретної цифри після заливки. Вони показують, що в самих сторінках більше
немає того, що блокувало показ. Реальне LCP живого домену треба переміряти
після заливки — `node d5-median.mjs`.

### Зображення

`images.txt` — перевірка всіх 616 зображень на 67 сторінках:

- усі віддаються через `<picture>` у трьох форматах: **AVIF → WebP → JPEG**;
- `0` зображень **без атрибута `alt`**;
- `0` зображень **без `width` і `height`** — саме тому CLS дорівнює 0,000;
- 552 з `loading="lazy"`; решта — герої сторінок, які свідомо вантажаться
  одразу, бо відкладати LCP-елемент означає сповільнити показ;
- герой кожної сторінки має `<link rel="preload">` з `fetchpriority="high"` і
  тим самим `imagesrcset`, що й сама картинка.

Lighthouse лишає одне зауваження на ~17 KB: ідеальною для фото міста була б
ширина між наявними 600 і 800 px. Ми свідомо лишаємо 800: 600 на екрані з
подвійною щільністю помітно м'якше, а різниця — 17 KB у фото, яке вантажиться
відкладено.

### Мобільна версія

`mobile-screenshots/` — 54 знімки: п'ять типів сторінок × три ширини
(360 / 390 / 414 px) × повна сторінка і перший екран, двома наборами — з
живого домену і з поточної збірки. **Горизонтального прокручування немає
ніде.** Деталі про формат знімків — у `README.txt` поруч.

### Best Practices 75

Цей бал знижують рівно дві речі, обидві — сторонні cookie від Google
Analytics і Google Ads. Прибрати їх можна тільки прибравши аналітику й
рекламні теги, тобто саме те, що замовлено. Це не дефект верстки.

### INP

`INP` — польова метрика: PageSpeed Insights показує її лише тоді, коли домен
набрав статистику реальних відвідувачів у CrUX. Для нового домену її ще немає.
Замість неї наведено `TBT` — лабораторний показник відгуку, за яким Lighthouse
і оцінює інтерактивність. Він у межах норми на всіх сторінках.

## D8 — Структурована розмітка

**Тека:** `d8-structured-data/`

| Тип | На хостингу | У збірці |
|---|---|---|
| `TaxiService` | відсутній | є |
| `Organization` | відсутній | є |
| `LocalBusiness` | відсутній | є |
| `Service` | є | є |
| `Offer` (ціна + валюта) | є | є |
| `FAQPage` | є | є |
| `BreadcrumbList` | є | є |
| `WebSite` | є | є |

Окремо варто сказати про попередню версію цієї перевірки: вона повідомляла, що
`TaxiService` і `Organization` відсутні **всюди**. Це була помилка самої
перевірки — вона шукала `"@type":"TaxiService"` текстом, а бізнес оголошений
кількома типами одразу:

```json
"@type": ["TaxiService", "LimousineService", "LocalBusiness", "Organization"]
```

Так писати можна і правильно, просто текстовий пошук цього не бачить. Нова
перевірка розбирає JSON і працює зі списком типів. На хостингу цих сутностей
справді немає — але тому, що там стара збірка, а не тому, що їх не написали.

Перевірити незалежно:

- https://search.google.com/test/rich-results?url=https://ridetoalps.com/
- https://validator.schema.org/#url=https://ridetoalps.com/

## Що лишилося зробити

**На нашому боці — нічого не лишилося.** Усе нижче потребує або заливки на
хостинг, або доступів, яких у нас немає.

| # | Дія | Хто | Наслідок, якщо не зробити |
|---|---|---|---|
| 1 | Залити поточну збірку (`node build-deploy.mjs`) | власник хостингу | три статті блогу лишаються 404; подій GA4 немає; `www` дублює сайт; LCP лишається 4–5 с |
| 2 | Після заливки запустити `node indexnow.mjs` | будь-хто з проєктом | Bing/Yandex не дізнаються про сторінки швидко |
| 3 | Додати домен у Search Console і Bing Webmaster Tools, підсунути sitemap | власник облікових записів | індексація повільніша; немає даних пошуку |
| 4 | Вимкнути в GTM теги `click_whatsapp` і `click_phone` | власник GTM | кліки рахуються двічі |
| 5 | Вирішити, чи потрібен `deposit_paid` | замовник | видно кліки на оплату, не видно оплат |

## Як перевірити все самостійно

Скрипти лежать у корені проєкту, кожен пише свій файл у цю теку:

```
node d1-live-sweep.mjs     усі адреси sitemap на живому домені
node d3-indexnow.mjs       ключ IndexNow, доступність, тестове надсилання
node d5-median.mjs         PageSpeed: живий домен і збірка, по 3 проходи
node d5-images.mjs         усі зображення: формати, alt, розміри, lazy
node d5-shots.mjs <base> <tag>   мобільні скріншоти 360/390/414
node d8-validate.mjs       структурована розмітка
```

Окремо — постійні перевірки самого сайту, які мають проходити перед кожною
заливкою:

```
node check-links.mjs       3426 посилань на 67 сторінках, биті посилання
node check-layout.mjs      переповнення, приховані елементи, помилки JS
node check-grid.mjs        вирівнювання по сітці на всіх ширинах
node check-consent.mjs     згода на аналітику і що відмова тримається
```

Станом на 26 листопада всі чотири проходять.
